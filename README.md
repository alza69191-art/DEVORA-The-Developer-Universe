# DEVORA — The Developer Universe

DEVORA is an independent developer platform. The web application is built with Next.js and PostgreSQL; Forgejo is the Git hosting engine and runs separately on a server with persistent storage.

## Current delivery

This repository contains the DEVORA branded web dashboard, application shell, database health endpoint, initial PostgreSQL schema, migration runner, Render Blueprint, and a Docker Compose deployment for Forgejo.

**Important:** this is the deployable foundation, not yet a finished GitHub-equivalent service. Authentication, authorization, repository provisioning, Git transport, code browsing, pull-request workflows, CI runners, and AI integrations must be implemented and security-tested before public launch. The dashboard currently contains preview/sample metrics.

## Deploy the web application on Render

1. Create a Render Web Service from this repository and select branch `main`.
2. Use the included `render.yaml` settings, or set build command to `npm install && npm run build` and start command to `npm run db:migrate && npm start`.
3. Set `DATABASE_URL` to the **internal** connection string of your existing Render PostgreSQL database when the service is in the same region. Do not commit credentials. The migration creates a dedicated `devora` schema, keeping DEVORA tables separate from other applications in the same database.
4. Set `APP_URL` to the deployed `https://<service>.onrender.com` URL.
5. Keep `AUTH_SECRET` generated by Render. Never expose it in browser code.
6. Configure `FORGEJO_BASE_URL` and `FORGEJO_API_TOKEN` only after Forgejo is deployed on a persistent server.
7. Confirm `https://<service>.onrender.com/api/health` returns `{ "status": "ok" }`.

Render web services have an ephemeral filesystem by default. Do not store Git repositories or user uploads on the Render app filesystem. Persistent disks are a paid-service feature; host Forgejo on a persistent VM or another storage-backed host. The Forgejo Compose stack in `infra/forgejo` is intended for that host, not for a free Render web service.

## Deploy Forgejo on a persistent Linux VM

1. Install Docker Engine and the Docker Compose plugin.
2. Copy `infra/forgejo/docker-compose.yml` to the VM.
3. Create an untracked `.env` file in that directory with a strong random `FORGEJO_DB_PASSWORD` and your `FORGEJO_DOMAIN`.
4. Run `docker compose up -d`.
5. Put HTTPS reverse proxy (Caddy or Nginx) in front of port 3000; expose SSH port 2222 only if you intend to support Git over SSH. Configure backups for both named volumes.
6. Create a dedicated Forgejo service account and API token with the minimum required permissions. Store the token only in Render environment variables.

## Environment variables

| Variable | Required | Purpose |
|---|---:|---|
| `DATABASE_URL` | Yes | PostgreSQL connection string |
| `AUTH_SECRET` | Yes before auth is enabled | Server-side signing/encryption secret |
| `APP_URL` | Recommended | Canonical public URL |
| `FORGEJO_BASE_URL` | When Git engine is connected | Private/server-side Forgejo URL |
| `FORGEJO_API_TOKEN` | When Git engine is connected | Server-side Forgejo API token; never expose to client |

## Local development

```bash
npm install
cp .env.example .env.local
npm run dev
```

Run migrations against a development PostgreSQL database with `npm run db:migrate`.

## Security and release gates

- Implement authentication, email verification, password hashing, session rotation, CSRF protection, rate limits, and account recovery.
- Enforce repository privacy and workspace membership on every server-side request.
- Never return Forgejo tokens, database credentials, or secret environment variables to the browser.
- Add malware/secret scanning, quotas, audit logging, backups, and restore tests.
- Add integration tests for repository creation, clone/push/pull, issues, reviews, and permissions.
- Do not advertise the platform as production-ready until these gates pass.
